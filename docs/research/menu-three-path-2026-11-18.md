# Menu 三路同场景对照

## 文档 Menu 关闭日志已支持局部输入重绘

普通文档 Menu 的关闭日志不再必然废弃 GPU 输出。新增可选的同步 `BackdropSnapshot.mutate(records)` 认证入口；没有实现该入口的来源维持原来的失效规则，返回 false 或抛错立即恢复原生材质。SDK 菜单状态、焦点和弹簧没有改动。本轮仍为本地开发变更，未提交、推送、发布或更新生产预览。

### 重画有界文本区，不以旧像素忽略真实日志

文档绘制器把符合条件的普通文本滚动区拆成保留的 Canvas2D 层，复用现有 DOM Range 分行及基线定位。文字、行节点、布局或样式变化时，同步重画该视口；不变的静态 SVG 批次仍复用。然后合成来源、递增 revision 并更新现有 GPU 光学。它不是任意 DOM 自绘，也不是 GPU 纹理脏矩形上传：输入变化后来源合成与光学仍有成本。

新层仅接纳可认证的平面文本、纯色背景和实线边框，不接纳复杂文字效果、嵌套滚动、未知图像或旋转/缩放祖先。它只分配视口大小，不因日志增长保存整段历史位图；共享 4,194,304 设备像素预算、单轴 8,192 像素限制，并限制遍历规模。现有嵌套滚动仍使用原有保留内容方案。无法认证时继续回退，不把旧像素当作新输入。

### 验证检查实际像素，不把虚拟时钟当性能

- 回归先在原实现失败：改字并追加真实日志行导致原 GPU surface 消失。修改后检查同一 surface 保留、固定菜单几何下光学像素变化，并与强制重捕获比较；删除一行也要求擦除旧像素并保留 surface。
- 真实 Escape 关闭确实追加业务日志，检查关闭可见阶段保留同一 surface，并直接读取 Canvas PNG 验证多份不同光学输出。已完成的明暗、1280/390、DPR1/2代表运行记录了18–19份可见采样及同等数量的不同输出。菜单已隐藏且 lens opacity=0 后的资源释放不计作可见缺帧。该检查插入读回并使用虚拟时钟，不证明真实刷新频率或窗口逐帧呈现。
- 在同一文本区插入不支持的 Canvas 会恢复可见原生材质，移除后可重新捕获。正文/代码、叠层、双轴内部滚动、窗口滚动、焦点及 Chromium/WebKit无GPU回退检查仍执行。

### 文字栅格不等价，不能宣称零画质变化

同步层使用 Canvas2D `fillText`，不是旧 SVG 文字图像解码。独立关闭新层的模块响应对照包含单行/八行、滚动、整数/小数位置、DPR1/2，八种原始来源位图均有差异：DPR1每图1,964或5,481像素不同，最大通道差47；DPR2每图5,616或15,766像素不同，最大通道差214。比较的是420×270 CSS px的来源位图，不是最终模糊/折射输出；不能把全图平均值当作文字质量无损证明。两种文字截图已检查，同步版本部分字缘更重。光学 shader 与卷积精度未改，不代表输入文字栅格相同。

照片 Menu 的来源边界缺口仍未解决；冷启动准备、任意富文本变更、主线程阻塞下原生合成滚动同步也不在此次验证范围。未新增前台帧时、物理显存、功耗或原生 Safari/iPhone 成绩，不以18–19份受控输出换算FPS。前一阶段父输出合成的1级通道差异及WheelPicker测试失败记录继续保留，不宣称全仓验收。

证据：`.amp/in/artifacts/menu-continuity/input-red.log`、`input-matrix.log`、`input-final-matrix.log`、`input-fallback.log`、`input-glass-tests.log`、`text-svg-parity.json`、`text-svg-*.png`及`menu-input-*.png`。独立文字对照探针保留为`menu-text-parity-source.txt`。

## 上一阶段：保留输出空间，关闭输入变化仍需重建

本轮只完成局部稳定化，尚未完成真实 Menu 全过程连续光学。修改位于 `packages/glass/src/scene-snapshot.ts`、`apps/docs/src/lib/menu-backdrop/vector-paint.js` 和已有的 `apps/docs/test/menu-document-scene.mjs`。未提交、推送、发布或更新生产预览；以下检查使用当前开发服务，不沿用下一节生产预览的性能成绩。

### 输出不再随每个弹簧几何重新分配

2D 输出 Canvas 随光学目标保留量化空间，每次重绘先清空，再仅写入当前可见区域。CSS transform 维持原来的像素间距和向上取整裁切；它没有以缩放旧玻璃图替代新光学计算。子菜单从父菜单取样时显式裁切可见像素，避免把预留空间缩进父菜单的图像。回归要求展开中至少三种 GPU 几何，而输出存储尺寸最多两种。

独立旧/新模块响应对照覆盖明暗、DPR1/2、六组非对称缩放/平移/过冲/往返，共24种状态。根输出的可见 PNG 全部一致，显示像素间距在可见边缘的累计差小于1/32 CSS px。将父输出继续交给文档合成后，严格零差检查未通过：24种中有3种分别在11、1、18个像素出现最大1个8位通道值的差异，每张为1000×1000像素；其余21种完全一致。不把这项结果记为完整叠层逐像素零差。故意让新输出继续使用旧的整幅 Canvas 取样作为负对照，24种均出现差异，最大单通道差145，证明检查能发现预留空间被错误缩入的问题。

这项改动增加驻留2D输出空间。250×146 CSS px、DPR2的样本在过冲后保留768×512像素，RGBA8逻辑载荷为1,572,864 bytes，相比原先静止500×292像素的584,000 bytes增加988,864 bytes，约0.943MiB。六组状态的输出存储尺寸由六种降为DPR1一种、DPR2两种。这里只计输出 Canvas 的RGBA8逻辑载荷，不是整个管线的显存、物理驻留、功耗或帧时测量，也不能据此宣布提速。

### 关闭缺口来自真实输入变化，不能无条件忽略

普通文档示例在关闭时向 Console 追加日志 `<li>`。诊断已确认 source MutationObserver 因该 childList 更新废弃旧快照，且此时菜单来源仍为 ready。日志处于光学输入范围，不能忽略、推迟业务更新或拿旧像素续帧来声称连续。捕获仍包含异步文档遍历、SVG编译与解码，当前未实现任意动态DOM的逐帧增量重绘。

照片 Menu 另有独立边界问题：收起至触发器附近时，完整模糊/折射采样邻域可能超出照片来源。当前回退保护输入正确性；后续需要补齐完整来源区域，而非扩大资格声明或拉伸照片边缘冒充页面内容。两种缺口均未在本轮解决。

## 实际光学更新：最终 shader 输出进入了原生窗口画面

环境仍为 M2 Pro、macOS27.2、Playwright WebKit27.2、DPR2，复用相同生产预览与照片菜单；本轮视口1280×1000 CSS px。用 ScreenCaptureKit 仅捕获该测试浏览器窗口，目标采样60Hz，保留各原生样本的PTS、状态、编码写入结果，不使用 Playwright 截图循环驱动动画。它是窗口合成结果，不是物理屏幕扫描或光子延迟测量。

诊断版仅在浏览器内拦截 WebGL 调用，在最终 material fragment shader 的输出内写入60×5 CSS px条码，与该次光学输出使用同一个最终 draw。条码包含8位递增提交编号、两组奇偶校验和彩色定位端点；不是另盖一个随rAF走的DOM编号。产品源码和生产文件没有修改。录屏离线解码后，与提交时间、surface uniform和展开阶段关联。

| 主题 | 三次展开中识别到的不同输出编号 | 对应不同显示宽度 | 已识别更新间隔中位数 | 各次最长已识别更新间隔 |
| ---- | ------------------------------ | ---------------- | -------------------- | ---------------------- |
| 亮色 | 19、19、21                     | 19、19、21       | 约17ms               | 50.6、34.9、34.5ms     |
| 深色 | 20、20、22                     | 20、20、22       | 约17ms               | 34.5、34.3、34.8ms     |

六次展开阶段约494–590ms；首个可解码光学编号在pointerdown后约115–221ms出现。这包含接管条件、实际合成和条码可读性，不能当精确GPU接管时刻或首像素延迟。早期无编号帧不应算作完整GPU折射更新。不能用19–22除以整个动画时长作为稳定FPS，因为前段仍有回退，后段才观察到光学编号。

最终亮/暗录屏分别有406/408个成功编码的complete样本，无编码背压导致的complete样本丢弃；亮色另有1个idle样本，未当成新画面。所有成功解码编号均能找到已提交的draw，编号不倒退，未发现比提交更早超过5ms的解码样本。亮、暗各7次原生前台边界检查匹配；DOM可见和焦点检查通过。这里仍不是每次显示刷新都必然被捕获的保证。未解码或没被观察到的提交不能直接判为产品丢帧，多次提交也可能是同一几何的重复工作。

### 不是只更新编号，也不是把CSS运动当成光学更新

- 独立像素诊断完全禁用条码，最终draw后读取GPU输出。90次读回的固定16×16像素区域alpha全部为255，仅计算RGB摘要，得到76个不同摘要。三次展开内分别为18/21、20/22、21/22个不同RGB摘要/样本。全画布RGBA得到80个不同摘要。这证明光学画布内部的颜色确有变化，不只是DOM位置、外缘alpha或诊断条码改变。读回会同步并扰动负载，该运行不用于帧时或呈现速度排名。
- 冻结负对照在每次菜单建立后保存完整最终GPU图像，随后继续执行原动画与光学提交，但最终shader改为输出保存的旧图像，连同旧编号一起冻结。三次展开仍提交23/42/25次，其中20/37/21次输出旧图；原生录屏每次仅显示冻结前及冻结时的3个不同编号，此后没有显示后续提交的新编号。录屏可见外框/文字继续展开、旧玻璃形状与新边缘失配。检测因此能区分动画继续与光学真正更新。
- 未改shader的独立原生录屏也已保留并查看，用于确认正常展开外观；它没有条码，不能独立承担逐帧归属证明。诊断录屏、负对照和未标记录屏均不是三路性能排名的新样本。

### 结论与测量限制

已排除“菜单动画期间一直只显示一张静态玻璃图”的解释，实际光学颜色改变且多份新最终输出进入窗口合成画面。尚不能声称全程真实折射、每个刷新周期都更新、稳定60FPS，或与旧模糊等性能。可解码更新间隔仍有约34–51ms尾部；尚未区分全部调度、提交、合成及捕获成本。没有真实Safari/iPhone或最终屏幕扫描证据。

初版录制器未初始化AppKit而失败，初始化后录制成功。早期条码放在圆角边缘、使用浮点位提取且从边缘取样，观察到未知编号或倒退，未纳入正式统计；最终改为底部中央、整数位编码、中心取样及校验，并重新录制。不能把早期误码归为产品旧帧倒退。独立DOM时钟画布也未留在最终DOM，因此不使用它作为同步证据；窗口PTS才是原生时间依据。

证据在`.amp/in/artifacts/menu-optical-*`：`summary.json`、`evidence-check.json`、`live-{light,dark}.json`、对应`.mov`和`.mov.json`、逐帧`-decoded.json`、`pixels-light.json`以及`freeze-light.json`。保留采集、原生录屏和解码脚本的`*-source.txt`源档。源码入口是`packages/glass/src/scene-backdrop.ts`的动态render调用和`scene-optics.ts`最终material draw。所有测试浏览器与录屏进程已关闭，既有服务未改动；本轮仅更新本地研究记录，没有修改产品、提交或发布。

## 上一轮三路回调间隔对照

本轮同场景前台对照中，新管线没有胜过旧 WebKit 路径或原生模糊基线：展开 P95 为亮色31ms、深色34ms，另外两路均为18ms；收起和打开后静止保持段基本持平。去掉每组首次展开后，新管线仍为30/33ms，另外两路仍为18ms。这是当前照片 Menu 接入方案的成绩，包含必要回退，不是全程 GPU、等画质或 Safari/iPhone 性能结论。

## 比较的是同一个 Menu，而不是两个工作量不同的页面

使用已有生产预览 `/cn/glass-lab?pipeline=components`，1280 × 1250 CSS px、DPR2，菜单为“照片选项”，包含同样三项文字，稳定尺寸均为 250 × 146 CSS px，模糊参数均为 15.3px。照片、其余控件、SDK 交互、弹簧时间线、主题与布局保持一致，只隔离目标 Menu 的光学路径。

| 名称             | 目标 Menu 路径                     | 保留和移除                                                                                |
| ---------------- | ---------------------------------- | ----------------------------------------------------------------------------------------- |
| 新管线           | scene GPU 折射，输入不满足时仍回退 | 保留动态轮廓、材质和既有回退                                                              |
| 旧 WebKit 路径   | 原生 backdrop blur + 既有轮廓      | 保留 moving contour 和 resting fitted rim                                                 |
| 原生模糊隔离基线 | 同一原生 backdrop blur 和材质色层  | 仅目标 Menu 跳过自定义 contour 与 resting fitted rim，保留交互、动画、阴影和原生 CSS 轮廓 |

第三项是测试隔离版，不是另一套已发布组件，不是 macOS 原生 Menu，也不是零 JS。它仍需现有 Menu 几何同步和材质层管理。WebKit 的旧默认 Menu 原本就不是 SVG 背景折射；Chromium 的旧 deferred Menu 也会在运动中使用原生材质，静止后才接完整光学。不能把它们统一称为“全程旧 SVG”。

实现隔离仅发生在此测试浏览器的资源响应中，未编辑产品源码或磁盘上的生产 bundle。三路都接收同一份带条件开关的响应。脚本对替换点做唯一性断言，并将原 bundle SHA-256 和逐处替换保存在原始结果中。照片页保持其余组件使用 scene，仅让目标 Menu 选择旧 nativePaint 分支，避免整页切换带来的混杂。

## 已核实真实分支，不只看名称

亮、暗各三路都通过：新路径静止时有 scene 输出；旧路径无 scene、保留 contour；原生基线无 scene，且 contour/fitted-rim 跳过计数均大于零，相应自定义标志不存在。两条原生路径的独立 paint 层使用 `blur(15.3px)`。画面截图后再次确认 scene 状态，并通过 Escape 关闭与触发器焦点恢复检查。六组运行均无页面脚本错误。

scene 并非整段开合无条件启用。正式帧时样本中，新管线亮色展开264/361个回调、收起140/403个回调可见scene标记，深色分别为268/365、138/401。这里是DOM状态覆盖率，不是呈现证明；不能把回退帧当成完整GPU折射帧。两条对照路径均未出现scene标记。

普通 Menu 文档页的初步分支 smoke 也观察到更低的 scene 覆盖率；这些不是前台性能样本，未纳入排名。照片页的结果不能直接代表正文/代码捕获的成本。

## 新管线菜单增加 18.28 MiB 的显式 RGBA8 纹理峰值

以亮、暗各一次开合、独立 GL 插桩运行统计 `texImage2D/3D` 的 RGBA8 分配、重新分配和删除事件，按时间合并各 context，而不是相加各自峰值：

| 指标                         | 亮色                             | 深色                             |
| ---------------------------- | -------------------------------- | -------------------------------- |
| 打开前整页已跟踪 RGBA8       | 18,120,960 bytes                 | 18,120,960 bytes                 |
| 新管线目标 Menu 新增并发峰值 | 19,169,280 bytes（18.28125 MiB） | 19,169,280 bytes（18.28125 MiB） |
| 新管线整页并发峰值           | 37,290,240 bytes                 | 37,290,240 bytes                 |
| 关闭后目标 Menu 的已跟踪纹理 | 0 bytes                          | 0 bytes                          |

旧路径和原生基线没有新增这组 SceneOptics 纹理。**这不表示它们显存为零**：浏览器原生 blur 中间层、共享 contour 的 drawing buffer、Canvas2D、合成器缓存、程序/驱动资源都不在此 RGBA8 账本内。删除 API 也不证明驱动立即回收了物理驻留内存。本轮未取得三路可归属的物理显存总账。

## 144个动画阶段完成，展开尾帧仍较长

用户解锁后的正式运行按 GPU → 旧路径 → 原生基线 → 原生基线 → 旧路径 → GPU 顺序，各独立浏览器、每组六次开合，亮暗分开，共12次独立启动、144个动画阶段。240次原生前台PID边界检查均匹配，逐帧DOM visible/focused也全部为真，无页面脚本错误。这不是连续原生前台审计，不能排除边界间极短的切换。

| 路径             | 展开P95，亮 / 暗 | 暖展开P95，亮 / 暗 | 收起P95，亮 / 暗 | 展开超过33.4ms，亮 / 暗 |
| ---------------- | ---------------- | ------------------ | ---------------- | ----------------------- |
| 新管线           | 31 / 34ms        | 30 / 33ms          | 18 / 18ms        | 15/361、19/365          |
| 旧WebKit路径     | 18 / 18ms        | 18 / 18ms          | 18 / 18ms        | 2/406、2/388            |
| 原生模糊隔离基线 | 18 / 18ms        | 18 / 18ms          | 18 / 18ms        | 2/393、2/401            |

三路展开/收起的中位间隔均17ms；打开后最后一组约1.2秒静止保持段P95均18ms。这个短静止段没有显示新管线的调度优势，不能据此推断三路功耗相等。两次独立启动的新管线暖展开P95，亮色分别32/30ms，深色33/34ms；两条对照每次均18ms，展开差距并非只出现在某一次启动。

暖展开按每次独立浏览器剔除第一次展开，每条件剩10次。新管线暖展开中，亮色11/303个间隔、深色15/309个间隔超过33.4ms；两条对照对应暖样本均为零。首次展开的最长回调间隔，亮色新/旧/原生分别61/65/62ms，深色61/62/53ms；三路都有首次开销，不能仅把新管线尾帧归于启动。

首次菜单从pointerdown到resting的两次读数：亮色新619/536ms、旧620/536ms、原生617/542ms；深色新536/525ms、旧531/534ms、原生529/611ms。这是同一设计时间线的状态阶段总长，不是GPU执行时间或首像素延迟，不能用某次较早resting抵消长帧。首次菜单展开也不是冷网页加载。

帧时运行不启用GL插桩、截图、GPU query、同步readback或虚拟时钟；画面和资源诊断另跑。指标为相邻rAF回调的`performance.now()`墙钟间隔；pointerdown到resting为展开，Escape到surface移除为收起。各条件合并间隔后以floor(n×p)取分位数，不平均各组P95；回调不是统计独立的用户样本。它们不等于纯GPU时间、最终呈现FPS或输入到像素延迟。正式帧时没有使用历史版本或锁屏诊断数据。

## 当前收益是补足光学能力，不是这类Menu的默认提速

此场景的旧原生路径已经接近正常rAF节奏；新管线增加真实折射和一组显式纹理，却增加了展开尾帧。不能因架构由GPU实现就宣布比浏览器原生GPU模糊更快，也不应以本结果支持全组件默认替换。对旧SVG软件滤镜、不同面积或动态背景的收益，须单独同场景测量；本轮没有否定这些其它场景的可能收益。
