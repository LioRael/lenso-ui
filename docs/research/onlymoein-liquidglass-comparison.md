# onlymoein/liquidglass compared with current Lenso UI

Research date: 2026-11-07. Upstream is pinned to [`89f8b7360a4501940aba9b838710bceb56b23601`](https://github.com/onlymoein/liquidglass/tree/89f8b7360a4501940aba9b838710bceb56b23601), package version 0.11.2. Lenso base HEAD is `a6909502bd9128eac8bc3199fd1a368fab1900c4`, but this comparison reads the **current working tree**, including pre-existing modified and untracked glass/menu work. HEAD alone cannot reproduce the reviewed Lenso implementation. No component implementation was changed for this research.

## Decision

Borrow the measurement workflow and selectively prototype the new menu choreography. Keep Lenso's material ownership, shared union optics, continuous press lighting and Base UI semantics. Glass fusion, elastic motion, trigger morphing and sliding menu highlights already exist in Lenso. Upstream supplies a different visual model and newer fitted motion parameters, not a missing interaction foundation.

The clearest current source difference is the menu's shape trajectory: upstream squeezes the trigger into a drop, overshoots its center and content size, then closes through a separate droplet phase. Lenso currently interpolates the trigger into the popup using one clamped spring progress value. A reference-like opening therefore requires independent geometry channels; changing one spring constant cannot reproduce it.

## Evidence boundaries

- **Source verified:** implementation details and constants below were read from the pinned checkout and current Lenso files. Repository tests were inspected for what they cover. Their presence is not a fresh passing test result.
- **Upstream claims:** README parity numbers and video descriptions are the author's reports. They were not independently reproduced here.
- **Rendered observations:** recorded separately below when available. Source review does not establish appearance, animation smoothness or browser compositing correctness.
- **Not established:** native Apple equivalence, a cross-browser performance win, real iPhone acceptance, complete accessibility acceptance, or production readiness. No benchmark is inferred from source size or algorithm choice.

## Transparency and optical transfer

The transparency difference has a concrete implementation cause. Upstream's [glass recipe](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/src/styles.css#L162-L203) couples its transparency parameter to several channels: below 0.5 it adds tint; above 0.5 it moves toward clear glass by reducing blur from 15.3 px toward 1.3 px and interpolating contrast, brightness and saturation. Size also changes the regular recipe. Its [lens fit](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/src/internal/refraction.ts#L462-L500) repeats the blur choice and selects the nonlinear dark transfer only for regular-or-more-tinted glass where backdrop SVG filtering is supported. The [dark transfer](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/src/internal/refraction.ts#L342-L391) uses small/large luminance and chroma tables. This can make bright backdrops dim differently from gray ones; it cannot be reproduced with one translucent overlay.

Current Lenso [preferences:64](../../packages/glass/src/preferences.ts) treats `glassTint` primarily as sampled-face opacity (`min(1, 0.2 + 1.6 * tint)`) plus an endpoint wash above the midpoint. Its older `glassTransparency` preference is a separate path and must not be conflated with upstream's similarly named parameter. Lenso also has discrete material profiles and explicit Figma-derived paint/shadow approximations in [apple-material.ts:1](../../packages/glass/src/apple-material.ts). The two preference ranges are therefore not equivalent calibrations: numerical endpoints, blur and tonal transfer need separate comparison.

**Observed upstream limitation:** in the Chromium demo probe described below, changing inherited `--lg-transparency` from 0.5 to 1 updated the CSS expression but left the embedded lens blur at 15.3 px until a resize triggered refitting. The [refraction observer](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/src/internal/refraction.ts#L514-L536) observes size, while the demo compensates by nudging minimum width. Adapt the material model with Lenso's existing preference invalidation; do not import the demo's resize nudge as the public behavior.

**Adapt:** evaluate a coordinated clear-to-regular material transfer against matched backdrops rather than tuning only fill alpha. Preserve Lenso's material profiles, consumer preference contract, contrast behavior and shared-plane consistency. Upstream's tables are useful hypotheses and calibration samples, not independently verified native ground truth. A style change that looks clearer on one colorful wallpaper can lose labels on a bright photo; compare flat colors, gray ramps, text, images and moving content in both appearances and supported engines.

There is one useful upstream implementation experiment: its two **in-document masks alternate** because changing the active SVG mask path may not repaint in WebKit. This avoids loading a replacement mask image. Lenso currently encodes its scanline outline as a data SVG and coordinates prepared optics/material transfer. Prototype double-buffered in-document masks only if matching captures show mask decode/repaint gaps. A blanket switch is unsupported: Lenso's optical maps and live backdrop layering must remain synchronized, and upstream's comment is not proof of universal WebKit behavior.

For two equal circles aligned horizontally, upstream's distance formula gives a midpoint value of `gap / 2 - spacing / 4`; connectivity therefore begins below approximately `spacing / 2`, not at `spacing` itself (default 20 implies about 10 CSS px for this case). This is an analytic source inference, not a native measurement. Lenso describes its spacing as an approximate edge-to-edge threshold and uses a different taper. Matching prop values is not a fair silhouette comparison.

Upstream reserves 24 px around its group. Lenso expands its paint plane to transformed bounds and documents axis-aligned geometry and unsupported ancestor-only scripted transforms. Neither should be described as supporting arbitrary rotated/skewed merging. More members and a larger bounding area increase CPU geometry work in both implementations; Lenso additionally prepares optical maps. Measure moving groups rather than assuming the smaller upstream implementation is faster.

## Menu opening and closing

Upstream's [opening and closing tables](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/src/menu.tsx#L79-L174) encode independent width, height, center, item zoom and corner-roundness channels. Opening has 25 samples intended at 60 Hz, including negative width progress down to -1.48, center overshoot to 1.4 and item zoom to 1.28. Negative width is mapped to a positive squeezed shape, not a negative DOM width. Closing uses 10 main samples followed by 21 droplet/trigger-return samples. The geometry was fitted around a 192 x 52 trigger and 250 x 167 popup, then extrapolated proportionally.

Its [runtime](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/src/menu.tsx#L374-L536) waits three animation frames initially, updates shell width/height/position/corners, separately scales/blurs/clips the content, and restores the trigger during the closing drop. On interruption it finds the table row nearest the current height. That preserves an approximate height, not continuous width, center, zoom and velocity. Elapsed time is capped at 34 ms per callback, so dropped frames can lengthen wall-clock duration. Three frames also imply different delays at 60 Hz and 120 Hz. Do not copy these scheduling decisions without measuring them.

Current Lenso [menu presentation:104](../../packages/ui/src/utils/interaction/menu.ts) uses `createSpring(0, 600, 46)` for opening and tunes to `900, 57` for closing. It clamps progress into [0, 1], linearly interpolates dimensions, and uses the same scalar for corner treatment, content scale, blur and glyph transfer. The final lens dimensions stay fixed and the shell transforms around them. Lenso also reconciles the live moving trigger and Base UI positioner during each frame. This is a real morph, but it cannot reproduce the upstream ball/drop trajectory or independent content overshoot.

**Adapt:** prototype independent shell width/height/center/roundness and content zoom curves inside the presentation layer. Keep Base UI in charge of open state, collision positioning, dismissal, keyboard navigation, selection, focus and unmount actions. Test trigger shapes, upward opening, viewport collision, tall menus, content changes and rapid reversal. Preserve the existing `morphTrigger={false}` and `elastic={false}` behaviors. Treat the sample tables as one reference recording, not a universal menu timing contract.

**Avoid:** importing upstream's all-in-one menu component or replacing Lenso's public parts API. Upstream manually implements focus, navigation, link activation, top-layer placement and dismissal; Lenso already uses Base UI and includes checkbox/radio items and stacked/cascade submenus. See [Lenso MenuRoot:54, Positioner:321 and Popup:392](../../packages/ui/src/components/menu/menu.tsx), [presentation lifecycle:20](../../packages/ui/src/utils/menu-presentation.tsx).

## Elastic feedback and pressed light

Both implementations already use an analytic damped spring, rubber-band translation and anisotropic stretch. Both stop animating at rest and resolve immediately when hidden or reduced motion is requested. Lenso additionally guards scheduler re-entry while paint callbacks retarget springs; replacing its scheduler with upstream's smaller version would discard that protection. Sources: [upstream spring](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/src/internal/spring.ts#L1-L153), [Lenso spring:72](../../packages/glass/src/motion/spring.ts).

| Behavior            | Upstream                                                         | Current Lenso                                                                                       |
| ------------------- | ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Generic mouse press | Grow 6; press 417.6/29.2; release 230/23.7                       | Same generic constants                                                                              |
| Generic touch press | Grow 16; press 795/38; release 342/13.5                          | Grow 15; press 515/27.3; release 250/11.8                                                           |
| Actual GlassButton  | Uses generic upstream feel                                       | Size-dependent growth 12/14/20; release 230/31                                                      |
| Menu drag           | Scale 650/36; translation 600/30; bounded exponential resistance | Same press scale and resistance; release retunes to critical damping                                |
| Press ownership     | Inline element `scale`/`translate`, `data-pressed`               | Presentation custom properties; disabled/pending/editing guards, mouse leave and visibility cleanup |

Constants are stiffness/damping pairs. These are source values, not measured response-time equivalence. Upstream touch parameters aim for a brisker fitted press and oscillating return. Lenso GlassButton deliberately uses a non-oscillating return to avoid recrossing a fusion threshold. Its actual component overrides matter: reading generic `press.ts` alone gives the wrong prediction for button behavior. [Upstream usePress](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/src/internal/press.ts#L12-L88), [Lenso generic press:12](../../packages/glass/src/motion/press.ts), [GlassButton growth/release:29 and application:94](../../packages/ui/src/components/glass-button/glass-button.tsx), [menu feedback:18 and release:125](../../packages/ui/src/utils/interaction/menu-feedback.ts).

**Adapt conditionally:** compare fitted upstream touch constants on isolated controls before considering group use. A bounce on release is a product/motion decision, not evidence of a missing elastic implementation. Retain stable group contact and editing behavior. Keep press lighting independent of elasticity: Lenso already supports stationary controls, held pointers outside a member, disabled descendant guards, nested optical ownership and keyboard lighting. Upstream's group CSS retains local highlight overlays; copying it would reintroduce per-item light boundaries.

## Specific interaction risks worth verifying

These are **source-derived risks**, not reproduced browser bugs:

1. In [Lenso menu feedback:140](../../packages/ui/src/utils/interaction/menu-feedback.ts), pointer release calls `chosen?.click()`. This creates a fresh activation without the original pointer's Ctrl/Meta/Shift modifiers. Upstream [release handling](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/src/menu.tsx#L661-L709) forwards modifiers through a synthetic MouseEvent. Verify modified primary-pointer activation on `Menu.LinkItem`, then preserve native link behavior if the risk reproduces. Copying upstream's manual navigation layer is unnecessary.
2. Lenso captures every eligible pointer on popup press. Upstream exempts touch when its placement reports a scrolling menu. Verify long-menu touch scrolling, cancellation and accidental release selection on a real touch surface. Pointer capture by itself does not establish that scrolling is broken; browser gesture arbitration and CSS touch action determine the actual result.
3. A newly adopted sampled menu morph must preserve graceful interruption and dynamic geometry. Upstream's nearest-height restart and single initial geometry measurement do not prove continuity for rapidly reopened, resized or flipped menus. Lenso's live-anchor reconciliation and Base UI lifecycle should survive any visual adaptation.

## What the upstream parity evidence actually establishes

The [README](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/README.md#L201-L209) reports near-native flat-field color and fitted button/menu motion. Its embedded comparison video is labeled version 0.10, while the reviewed source package is 0.11.2. Do not present that video as evidence that every current implementation path was recorded.

The repository contains useful native SwiftUI versus Web/WKWebView fixtures on the same simulator and backgrounds. [The runner](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/parity/run.sh) builds an iPhone simulator app and Web production bundle; the build target says iOS 26 minimum, which does not independently prove which runtime produced the published iOS 27 captures. Record the actual runtime and device when reproducing.

- [Color fitting](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/parity/tools/fit.py) searches a CSS contrast/brightness/saturation model against measured samples. That is valuable calibration evidence for sampled conditions, not a bound on arbitrary photographs, text contrast, moving backdrops or the whole silhouette. Report error in the stated pixel domain; do not turn an RGB-level claim into perceptual equivalence.
- [Motion capture](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/parity/tools/motion.sh) includes large-button press and menu opening. [Tracking](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/parity/tools/track.py) thresholds one scanline and one column against gray, assumes a 3x device scale and labels frame indices at 60 Hz. It measures silhouette extent under those assumptions; shadows, blur, threshold choice and capture timing can bias bounds. It is not a compositor frame-time or input-latency benchmark.
- [Group comparison](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/parity/tools/merge.sh) captures static gaps 40, 14, 6 and 0 for [two 60 pt circles](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/parity/app/ParityApp.swift#L118-L131). This is a useful visual fixture, not quantitative evidence for continuous attach/detach motion, mixed shapes, multiple members or held shared lighting.
- [GlassGroup tests](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/test/glass-group.test.tsx) assert outline connectivity and DOM mask/rim agreement. The [jsdom configuration](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/vitest.config.ts) and [mocked ResizeObserver/pointer capture](https://github.com/onlymoein/liquidglass/blob/89f8b7360a4501940aba9b838710bceb56b23601/test/setup.ts) cannot establish browser repaint, geometry fidelity or performance.

Local tests already cover native activation/ref preservation, press cleanup, fusion overflow and shared lighting ownership: [glass-container.dom.test.tsx:61](../../packages/ui/test/glass-container.dom.test.tsx), [press-highlight.dom.test.tsx:22](../../packages/ui/test/press-highlight.dom.test.tsx). These tests also do not establish rendered acceptance. For a future implementation, add only cases that catch a concrete new failure; use matched browser/device captures for the visual questions.

## Rendered comparison and reproducible limits

The pinned upstream checkout was built in an isolated temporary directory using existing dependency links, then served at `http://127.0.0.1:4349`. In Chromium, the demo rendered and the “Sort by name” menu opened. No page errors were reported during that initial visit and menu interaction. Captures: [controls](/Users/leosouthey/.codex/visualizations/2026/11/06/01a1b223-ead1-7131-9aac-8dab90fa59a6/liquidglass-comparison/liquidglass-controls.png), [open menu](/Users/leosouthey/.codex/visualizations/2026/11/06/01a1b223-ead1-7131-9aac-8dab90fa59a6/liquidglass-comparison/liquidglass-menu.png). A still capture confirms the observed state, not the opening trajectory.

A direct Chromium probe on the regular button established an upstream invalidation limitation:

1. Initial inherited transparency 0.5 used embedded SVG filter `liquidglass-17` with Gaussian blur standard deviations `[15.3, 0.4]`.
2. Setting `document.documentElement.style.setProperty("--lg-transparency", "1")` and waiting 500 ms changed the CSS blur expression to its clear endpoint, but retained filter `liquidglass-17` and embedded blur 15.3.
3. Increasing the button's minimum width by 0.05 px and waiting 600 ms caused a new filter `liquidglass-35` with blur `[1.3000000000000007, 0.4]`.

This confirms that this path needs refitting beyond an inherited CSS-variable update. It does not establish every preference path is stale. The demo deliberately performs such a resize after the global setting changes; adopting the optical relationship requires proper preference-driven invalidation.

Lenso's local Menu documentation at `http://127.0.0.1:4337/en/docs/react/components/menu` was inspected for its current source and shell. There was no matched Lenso/upstream/native animation trace, no fresh native simulator run, no real iPhone test, no quantitative frame-time comparison and no complete second-engine sweep. The modifier and scrolling items above remain source risks. No exhaustive code audit or full visual acceptance is claimed.

## First implementation slices

1. **Coordinate transparency in the owning material layer.** Define the intended blur, luminance/chroma and face-fill behavior for existing `glassTint` endpoints, with preserved legacy preference semantics. Integrate invalidation with the existing observer. Verify actual embedded-filter values after a preference change without resizing, then compare flat ramps and moving photographic backdrops in both appearances. This directly addresses the concrete optical-model difference and the observed upstream update defect.
2. **Prototype menu geometry inside existing presentation ownership.** Give width, height, center, corners and content zoom independent curves; evaluate squeeze/overshoot and closing drop on a representative trigger. Preserve Base UI positioning, focus, selection, controlled state, cancellation and delayed unmount. Capture opening, closing and reversal over the same backdrop before deciding whether to keep the choreography. Include modifier activation and long-menu touch scrolling in that focused review.
3. **Measure moving fusion before changing its renderer.** Use the existing GlassContainer and a two-control fixture with matching physical gaps. Capture merge, split, press/release and a held light moving across the shoulder. Investigate mask publication or spring tuning only when those captures identify a concrete defect. Retain persistent union materials and shared light; upstream's group implementation is not a drop-in improvement.

These are proposed follow-up changes. This research changes only this report. Implementation tests, browser acceptance and landing gates remain for the actual changes.
